Scraper Commonalities

Research · 2026-04-20 · Terpenomics sprint: thin-API / thick-scripts

Two scraping scripts exist today: one for The Travel Agency (website scrape) and one for Brooklyn Organic Buds (Alleaves POS API). A third script, import_listings.py, consumes both outputs.

This research identifies what they share, what must stay source-specific, and what a minimal common module would look like.

Travel Agency

Leaflogix / Remix turbo-stream site. Single GET loop, slug-based SKU, 1s delay. ~314 lines.

Alleaves (Brooklyn Organic Buds)

Alleaves POS API. Two-pass: items catalog + inventory for in_stock. Cookie auth. ~260 lines.

~40 lines are copy-paste identical across both files today.

What Stays Scraper-Specific

Concern Why it can't be shared
Auth No auth (travel agency) vs cookie-based session (Alleaves) — fundamentally different
Fetch / parse Turbo-stream flat-array decoding vs Kendo form-encoded API with two passes
normalise() Source-specific field names, price logic, variant derivation, classification source
Dedup key Travel Agency uses the product slug; Alleaves uses id_item; next source will differ
Rate limit delay 1.0s (polite web scrape) vs 0.3s (authenticated API)
Pagination exit condition Travel Agency uses total_products count; Alleaves uses both page length and total_rows

Proposed: scripts/scraper_common.py

A minimal shared module. No pagination abstraction. No base classes. Just the shared data and pure functions.

Each scraper imports only what it needs:

from scraper_common import map_category, store_slug, now_iso, write_csv

Placement in scripts/ (not prototypes/) signals it's a stable dependency, not a throwaway.

Trade-offs

For shared module

  • CSV schema defined once — future scrapers can't silently diverge
  • Category enum owned in one place — adding a new POS source means adding keys to one file
  • ~40 lines of copy-paste eliminated
  • Consistent write_csv behavior (e.g. extrasaction="ignore") without remembering to add it in each scraper

Against / risks r005

  • Adds a file dependency — a bug in scraper_common breaks all scrapers simultaneously
  • Previously isolated scripts now have a shared failure mode
  • Solo project: copy-paste drift costs less than in a team codebase
  • At 2 scrapers, savings are real but modest

Verdict r004

Do it — but stay minimal. The CSV schema and category enum are shared contracts, not coincidental duplication. They will diverge and cause import failures if kept separate. Pagination abstraction is not worth it at this scale. Keep scraper_common.py to pure functions and data — no classes, no protocols, no I/O beyond write_csv.

Claims: r001 (CSV schema identical), r002 (write_csv near-identical), r003 (CATEGORY_MAP shared enum), r004 (recommendation: create scraper_common.py), r005 (risk: shared single point of failure)
