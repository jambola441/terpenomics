Decision Brief: Lab Report Parser — Files API Migration & CheckWeedNY Integration

Date: 2026-04-12  |  Audience: engineers  |  Phase: Compiled  |  Claims: 44 active

Executive Summary

Migrate the COA lab report parser to use the Anthropic Files API (upload + single document block) instead of per-page base64 image batching — this has shipped as a working prototype with extraction parity confirmed. In parallel, integrate the CheckWeedNY API as a "lookup first" layer: use ?batch=<batch_id> as the primary key, falling back to ?brand=&product=, and skip Claude entirely for records with parse_confidence ≥ 0.7 and terpene_count > 0. A bulk-sync script prototype exists to backfill existing products. Two open risks — terpene name normalization and the 28% confidence miss rate on flowers — require attention before production rollout.

Recommendation

1. Ship the Files API migration (ready now)

Replace services/lab_report_parser.py with the Files API approach r013:

  1. Remove PyMuPDF rasterization entirely (rasterize_pdf, _extract_from_page, _merge_extraction — ~60 lines removed p003)
  2. Upload raw PDF bytes via client.beta.files.upload(file=("report.pdf", BytesIO(pdf_bytes), "application/pdf")) r002
  3. Send ONE client.beta.messages.create call with a document block, source.type = "file", file_id = upload.id r003 r016
  4. Delete the file in the finally block
  5. Retain all Pydantic models unchanged p001
Required: Add betas=["files-api-2025-04-14"] to every messages.create call that uses a file_id source r001 r016.

1-page latency is ~0.9s worse p006; crossover to faster occurs at 2+ pages where the old approach fires an early exit after page 1 x001 x002.

2. Integrate CheckWeedNY as a lookup-first layer

Before invoking the Claude parser, attempt a CheckWeedNY lookup:

1. If product has a LabReport with batch_id:
      GET /v1/coas?batch=<batch_id>          → 1 exact result (x004)

2. Else if product.brand is set:
      GET /v1/coas?brand=<brand>&product=<name>
      → pick highest parse_confidence with terpene_count > 0

3. If found AND parse_confidence ≥ 0.7 AND terpene_count > 0:
      GET /v1/coas/<id>   → terpenes [{compound, value_pct}]
      → map to ProductTerpene, skip Claude entirely

4. If found but terpene_count = 0 AND pdf_url is set:
      Download pdf_url → run through Files API parser
      → saves user from uploading PDF manually

5. Miss / low confidence → existing upload+parse flow unchanged

Auth: X-API-Key header r019. All filter params are partial and case-insensitive r029.

3. Run the bulk-sync script to backfill existing products

prototypes/checkweedny-bulk-sync/sync.py implements the above flow as a standalone CLI script p007 p009:

# Dry run first (no DB writes — default)
python sync.py --brand "Ayrloom"

# Write terpenes, skip products that already have them
python sync.py --write --skip-existing

Before running at scale, resolve the normalization gap (see Risks — x007 p008).

Evidence Summary

Files API — core mechanics

  • Upload r002 (documented): client.beta.files.upload(file=("document.pdf", open(...), "application/pdf")) returns a file_id.
  • Message reference r003 r016 (documented): Use client.beta.messages.create with document block, source.type = "file", and the beta header.
  • Mechanism r007 (documented): Anthropic extracts text + converts each page to an image — identical to what the old rasterization loop did manually, but server-side.
  • Limits r004 r008 (documented): 500 MB/file, 600 pages/request (100 for base64), ~100 req/min, 32 MB payload cap.
  • Billing r012 (documented): Upload/list/delete are free. File content in messages billed identically to inline content.
  • Beta constraints r011 r014 (documented): Not ZDR-eligible. Breaking changes possible before GA.

Files API — prototype results

  • Payload reduction p002 (tested): 1-page COA → current sends 147,849-byte base64 PNG; Files API sends 1,977 bytes at message time. 99% reduction.
  • Extraction parity p005 (tested): Identical results on a live 1-page COA — 10 terpenes, 8 cannabinoids, same confidence score.
  • Latency p006 x001 x002 (tested): 1-page: old 5.08s, new 6.01s (+0.93s). Crossover at 2+ pages because old approach exits on first match; new always processes whole PDF in 1 call.
  • Code reduction p003 (tested): Removes 3 functions (~60 lines). No new dependencies.
  • API call count p004 (tested): Old = 1 call (single-page). New = 3 calls always (upload + messages + delete). Net reduction for multi-page PDFs.

CheckWeedNY API

  • Dataset r018 (tested): 32,518 COAs, 671 clients, 532 brands, 26 labs. Spans 2008–April 2026.
  • Filter params r029 x003 (tested): ?batch=, ?brand=, ?product=, ?lab= — all partial, case-insensitive. ?batch= returns exactly 1 result for a full batch string x004.
  • List schema r020 (tested): id, brand_name, product_name, batch_number, terpene_count, parse_confidence, pdf_url, inline cannabinoid pct fields, pass/fail booleans.
  • Detail schema r021 (tested): Adds terpenes: [{compound, value_pct}] plus pesticides, solvents, heavy metals, microbials, mycotoxins nested arrays.
  • parse_confidence r025 (tested): 0.0–1.0. ≥ 0.7 reliable; ≤ 0.5 garbled — fall back to Claude.
  • pdf_url r024 (tested): Present on every record. Can be piped directly into the Files API parser.
  • Terpene coverage r022 (tested): Flower and concentrate records typically have terpene data. Ingestibles/tinctures/topicals have terpene_count = null.

Bulk sync prototype

  • Lookup logic p007 (tested): Batch-first, brand+product fallback. Dry-run default.
  • Normalization p008 (tested): 30-entry map converts API names to canonical names. Unmapped names pass through as-is.
  • CLI p009 (tested): Flags — --write, --skip-existing, --product-id, --brand, --min-confidence.

Resolved Conflicts

x004 supersedes r026 step 1

What disagreed: r026 described the primary lookup as "search by brand (required) + paginate through results to match by batch_number client-side." x004 showed this was wrong — ?batch=<batch_number> returns exactly 1 result directly; no brand filter needed, no client-side scanning.

How resolved: Both claims were tested tier. Manual adjudication favored x004 because x003 had already confirmed ?batch= works, and x004 is a narrower factual finding that directly contradicts an untested assumption in r026 step 1.

Winner: x004. The correct primary lookup is GET /v1/coas?batch=<batch_number>.
